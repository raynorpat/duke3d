# macOS App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a native macOS launcher for Duke and BUILD with external installations used in place and optional bundled data.

**Architecture:** Keep the SwiftUI launcher and C/SDL executables in separate processes. Add a shared read-path resolver and headless game-data preflight, then package the launcher and helpers through CMake. Bundled-data launches use a writable Application Support workspace.

**Tech Stack:** C99, CMake 3.24+, SDL2 2.32.10, SwiftUI/AppKit/Foundation, macOS 12.0+ for app builds.

**Spec:** `docs/superpowers/specs/2026-10-23-macos-app-design.md`

## Global Constraints

- `DUKE3D_MACOS_APP` defaults OFF; requesting it on another platform fails clearly. Enable Swift only for app builds.
- App builds use `DUKE3D_FETCH_SDL=ON` and static SDL; normal CLI build dependencies remain unchanged.
- Retain `bin/duke3d` and `bin/build`; do not implement runtime release switching.
- Never commit proprietary data. `DUKE3D_MACOS_GAME_DATA_DIR` is optional and empty by default.
- External installations are used in place. Bundled resources are read-only; relative output goes to `~/Library/Application Support/Duke Nukem 3D/Workspace/`.
- Preserve case-insensitive reads, GRP-only lookup restrictions, legacy argument order and existing save/config locations.
- No shell launches, App Sandbox, auto-discovery, mod library, universal build requirement or notarization workflow.

## Review Focus

- Data lookup after BUILD changes directory: the selected source must remain absolute; cover this in Task 1.
- Malformed GRP counts/lengths and duplicate member names: no overflow or reads beyond EOF; preserve the engine's last-member precedence in Task 2.
- A stale selection or a slow validation finishing after a new selection: never launch the wrong source; cover this in Task 3.
- Child output large enough to fill a pipe, failed launches and close/reopen during a running child: remain responsive and preserve the session; cover this in Task 3 and live QA.
- Changing/removing bundled data or moving the app: no stale resources or original-build paths; cover this in Task 4.

## Task 1: Separate data reads from the writable working directory

**Files:** create `source/build/datapath.c`, `source/build/datapath.h`, `tests/datapath.c`, `tests/datapath.cmake`; modify `source/build/CMakeLists.txt`, `source/game.c`, `source/build/build.c`, `source/build/sdl_main.c`, `source/build/filesystem.c`, `source/build/tiles.c`, `source/global.c`, `source/astub.c`, `source/buildcfg.c`, `tests/CMakeLists.txt` as required by actual read call sites.

**Interfaces:** engine-owned, without game/Foundation dependencies:

- `int build_parse_datadir(int *argc, char **argv)`: consume `-datadir DIRECTORY` in place, preserve argv[0], all other argument order and the NULL terminator; return 0 or -1 with a stderr diagnostic. Store an absolute source directory without changing cwd. Reject missing/repeated/inaccessible directories.
- `const char *build_datadir(void)`: selected absolute directory, or NULL when unset.
- `int build_readpath(char *out, size_t capacity, const char *name, int base_only)`: resolve an existing readable loose file; return 0 or -1 without truncation. With `base_only`, use the selected data directory (cwd if unset); otherwise search cwd then the selected directory. Absolute names stay absolute. Keep case correction inside this resolver and never apply it as a write fallback.
- Keep pathname storage internal or caller-provided; report paths too long rather than overflowing legacy filename buffers.

- [ ] Write `datapath` fixture tests for argument compaction, no-option behavior, missing/repeated arguments, inaccessible source, relative-to-initial-cwd resolution, cwd-first overrides, source fallback, authoritative base GRP, absolute paths and mixed case. Use fixture directories containing spaces and Unicode; after selection chdir again and verify source fallback still works. Read a fixture asset and create an output with the same basename; assert the output is in cwd and the source bytes are unchanged.
- [ ] Configure/build `datapath_test` and run `ctest --test-dir build-macos-app -R '^datapath$' --output-on-failure`; expect failure before the resolver exists. Keep failure attributable to the missing behavior, not unavailable SDL or test data.
- [ ] Implement the resolver and integrate parsing before `_platform_init` in both real mains. The compacted argc must reach `_platform_init` and both legacy parsers. Remove the macOS .app-root chdir heuristic. Do not change ordinary no-option CLI lookup behavior.
- [ ] Use the resolver for the base GRP in both programs; feed loose read fallback into `kopen4load` only when `searchfirst == 0`. Audit raw read opens, especially ART pixel reopening, scripts, editor `names.h` (open read-only), `setup.dat`, RTS, palettes/tables and demo playback. Leave writes directed to their existing paths. Only touch files the audit identifies.
- [ ] Report demo-open and map-save failures at their existing call sites. A failed save must not report success or trigger a successful-save backup hook. Keep map formats and normal successful behavior unchanged.
- [ ] Run the resolver test and existing suite. Add an engine-level fixture check that loose source assets remain readable after cwd changes and that GRP-only reads ignore loose overrides. Manually exercise an editor save into an unwritable location during final QA.
- [ ] Commit: `macos: separate game data reads from working files`.

## Task 2: Add noninteractive data validation using the existing release fingerprints

**Files:** create `source/grpcheck.c`, `source/grpcheck.h`, `tests/checkdata.cmake`, `tests/grpcheck.c`; modify `source/game.c`, `source/CMakeLists.txt`, `tests/CMakeLists.txt`. Preserve `tests/game_helpers.c`'s existing CRC/mismatch contract.

**Interfaces:** consumes Task 1's selected data directory and read resolver:

- Move the existing fingerprint table, CRC implementation and `grpmismatch(int32_t, uint32_t)` into `grpcheck.c`; preserve `uint32_t grpcrc32(uint32_t, const unsigned char *, size_t)` and existing normal-startup warning behavior. Do not duplicate the table in Swift.
- `int duke_checkdata(int editor)`: print diagnostics and return 0 usable, 1 missing/unreadable/malformed, 2 known incompatible/unsupported release. Do not initialize SDL or mutate user directories.
- CLI: `duke3d -datadir DIRECTORY -checkdata` and `duke3d -datadir DIRECTORY -checkdata -editor`. Recognize these before copy protection, banners or SDL initialization; reject malformed check-mode arguments clearly. An ordinary game launch must not interpret `-editor` as a new gameplay option.

- [ ] Write synthetic GRP fixture tests: valid header/directory, missing GRP, short header, bad signature, oversized count, truncated directory, negative/overflowing member sizes and members extending beyond EOF. Use 64-bit checked offsets; cap accepted member ranges by actual file size. Verify duplicate names use the last archive entry, as the engine does.
- [ ] Assert `duke_checkdata` accepts an unknown structurally valid archive with a clear compiled-release diagnostic, requires game scripts for Play from loose files or members, permits editor data without CON scripts, and treats DUKE.RTS/demos/names.h/setup.dat as optional. Both modes require `palette.dat`, `tables.dat` and `tiles000.art` from the same lookup rules. Unit-test every known fingerprint against the compiled version, including unsupported Mac shareware; do not commit release data to exercise these decisions.
- [ ] Run `ctest --test-dir build-macos-app -R '^(checkdata|grpcheck|game_helpers)$' --output-on-failure` before implementation; expect the missing check mode/validator to fail. Run check-mode subprocesses with deliberately unavailable SDL video/audio drivers and a disposable HOME; assert no settings directory is created.
- [ ] Implement validation with bounded archive-directory reads and checked member offsets. Resolve base GRP authoritatively; use cwd/data loose precedence before GRP members for required assets. Keep normal launch warnings through the shared module. Test CRC matching as pure logic rather than fabricating copyrighted known archives.
- [ ] Re-run the targeted checks and all available native tests; compile a shareware configuration to verify version metadata and editor eligibility. Commit: `macos: validate installations before launching`.

## Task 3: Build the native launcher and test its data/process decisions

**Files:** create `source/macos/LauncherCore.swift`, `source/macos/LauncherModel.swift`, `source/macos/DukeLauncher.swift`, `tests/launcher_core.swift`, `source/macos/CMakeLists.txt`; register optional Swift tests through the macOS build configuration in Task 4.

**Interfaces:**

- `enum LaunchTarget { case game, editor }`.
- `enum DataSelection { case external(URL), bundled(URL) }`; distinguish an unresolved remembered selection from no saved selection. Never replace the former with bundled data implicitly.
- `enum SelectionState { case none, selected(DataSelection), unavailable(String) }`.
- `struct LaunchRequest`: immutable `executableURL: URL`, `arguments: [String]`, `workingDirectoryURL: URL`, `logURL: URL`.
- `LauncherCore.restoreSelection(bookmark: Data?, bundledURL: URL?) -> (selection: SelectionState, refreshedBookmark: Data?)` resolves source state; the model persists refreshed bookmarks in UserDefaults.
- `LauncherCore.launchRequest(selection: DataSelection, target: LaunchTarget, bundleURL: URL, workspaceURL: URL, logURL: URL, checking: Bool) throws -> LaunchRequest` creates launch/check requests. Checks invoke Task 2's `duke3d` mode; normal launch invokes the selected helper with `-datadir` and its absolute data path. Bundled data uses the workspace; external data uses its installation as cwd.
- `@MainActor final class LauncherModel: ObservableObject` owns selected source, per-target validation, the active Process and user-facing error/log state. UI observes this one model; no general plugin or process framework.
- Bundle metadata keys: `DukeGameVersion` (string) and `DukeShareware` (Boolean); use the existing CMake release settings, not a new version registry.

- [ ] Implement a small Foundation-only Swift test executable. Assert external selection overrides bundled data, explicit bundled choice clears an external bookmark, invalid remembered selection blocks fallback, cancellation preserves selection, stale bookmark refresh preserves the URL, and renamed/moved bookmarked directories either resolve or request reselection. Assert argument arrays preserve spaces/Unicode literally and source/workspace/log URLs are correct after moving the app.
- [ ] Test process behavior with a disposable child executable/script invoked directly by Process, without a shell command string: success, launch exception, nonzero exit, signal termination, large output written to a file, and a validation result arriving after a newer selection. Assert a running session rejects a second launch and does not reuse stale validation.
- [ ] Run `ctest --test-dir build-macos-app -R '^launcher_core$' --output-on-failure` and observe failures for unimplemented behavior, then implement Core and Model. Use a monotonically changing selection/validation identity to discard stale asynchronous results; do not retain cached validation across a launch.
- [ ] Implement the SwiftUI window with source/path/build release/status, Choose Folder, optional Use Bundled Data, Play, Open BUILD and access to the last-run log. Use NSOpenPanel for directories. Disable editor launch for shareware and disable any action whose preflight fails. Opening the chooser must not clear the current selection.
- [ ] Launch asynchronously and send stdout/stderr to a last-run file under Library/Logs/Duke Nukem 3D. Capture preflight output in separate temporary files, read after completion and remove them. Hide the launcher only after Process.run succeeds; restore/activate on termination. AppKit delegate handles reopen/focus and idle-close/active-quit semantics from the spec. A quit confirmation offers cancel or child termination; do not allow a second validation/launch while terminating.
- [ ] Run Swift tests and manually exercise native panel, error messages, launch/reopen/quit and keyboard navigation once Task 4 creates the bundle. Commit: `macos: add native installation launcher`.

## Execution notes

Tasks are sequential: validation depends on path handling, the launcher depends
on validation, and final packaging assembles all three. The Swift test target
and minimal optional CMake wiring may land together with Task 3 so its tests are
runnable before Task 4 finishes packaging. This is setup for that deliverable,
not an independent task. Use fresh tests and one separate final review rather
than parallel implementers touching the same startup and build files.

At execution start, choose/verify the workspace, run the available native
baseline, and keep per-task test results and decisions in the plan ledger.
Do not overwrite or remove the pre-existing untracked Python cache directories.
