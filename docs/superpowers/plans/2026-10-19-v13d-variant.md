# Duke Nukem 3D 1.3D and 1.4 Build Variants Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `DUKE3D_VERSION` CMake setting (`1.3D` / `1.4` / `1.5`) that builds a
1.3D (full or shareware) or 1.4 game from this tree. The 1.3D build runs the original
1.3D CONs, plays the five original 1.3D demos in sync, loads DOS 1.3D saves, and plays
multiplayer against itself.

**Architecture:** Version differences are `#if` guards on two ordered date macros, in
place in the existing files. `DUKE3D_GAMEVER` covers game code and `BUILD_ENGINEREV`
covers engine code. They mirror the gamesrc-ver-recreation project's `APPVER_DN3DREV`
and `LIBVER_BUILDREV`, so its guards port mechanically. The work is in four phases.
Each phase starts once the 64-bit sub-project it depends on has landed:

- A: research, now
- B: build and single player, after 64-bit sub-project 1
- C: demos and network, after sub-project 2
- D: DOS saves, after sub-project 3

Every difference found goes in the **Differences ledger** at the end of this file.

**Tech Stack:** C99, CMake ≥ 3.24 and CTest, SDL2. Research tools: `unifdef`
(`/usr/bin/unifdef`), Ghidra with an LE/LX loader, and DOSBox-X (for its debugger).

**Spec:** `docs/superpowers/specs/2026-10-19-v13d-variant-design.md`

## Global Constraints

- Nothing from the 1.3D releases goes in the repo: no CONs, GRPs, demos, saves or
  executables. Tests read them from `DUKE3D_V13D_DATA_DIR` (full) and
  `DUKE3D_V13D_SW_DATA_DIR` (shareware).
- Numbers measured from the DOS executables may be committed. These are reference state
  values, addresses and checksums, not game content. *(Plan decision.)*
- The default `DUKE3D_VERSION=1.5` build keeps its current behavior. The only exception
  is a real bug fix in shared code. That fix applies to all versions, gets a one-line
  comment next to it, and is called out in the commit message.
- The tree is not duplicated. Differences are `#if`/`#else` blocks in the existing files.
- Engine changes are logged in `source/build/VENDORED.md`, which is the existing rule
  for vendored code.
- Follow sub-project 1's conventions in any code it rewrote: `int32_t`/`uint32_t`,
  `SCRIPT_OFF`/`SCRIPT_PTR`.
- Tests that need 1.3D data exit with **77**, registered as CTest `SKIP_RETURN_CODE 77`,
  when their data variable is unset or the folder is missing. CI never fails for lack of
  data.
- Commit messages follow `AGENTS.md`: a subsystem prefix, one or two lines, and no
  metadata.
- The only multiplayer target is our own 1.3D build. Our build writes its own save and
  demo formats; the DOS executable never has to read them.

## Review Focus

1. **Bad version settings** must fail at configure time with a clear message, not build
   something wrong. Examples: `-DDUKE3D_VERSION=1.3` or `13d`, and
   `DUKE3D_SHAREWARE=ON` with `1.4`. *Test: Task 8 step 1.*
2. **A data folder holding the wrong edition**, such as the full release under
   `DUKE3D_V13D_SW_DATA_DIR`, must fail with "wrong edition". It must not show up as a
   desync or a CON error. *Test: Task 11 step 1.*
3. **A demo that isn't a 1.3D demo**, for example one recorded by the 1.5 build or by
   our native format, must be refused by the 1.3D build. It must not play garbage.
   *Test: Task 14 step 1.*
4. **Mixed multiplayer peers** must be refused at connect. That covers 1.3D vs 1.5 and
   1.3D full vs 1.3D shareware. *Test: Task 16 step 1.*
5. **A save from the wrong version or edition**, such as a 1.5 save, a shareware save in
   the full build, or a native save from another version, must be refused with a
   message. It must not crash or load corrupt state. *Test: Task 17 step 1.*
