# Duke Nukem 3D 1.0 and 1.1 Shareware Build Variants Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let `DUKE3D_VERSION` take `1.1` and `1.0` (shareware only). Each build must
run that release's original CONs, play its three demos in sync, load its DOS saves, and
play multiplayer against itself.

**Architecture:** This extends the 1.3D variant downward:
- `gamever.h` gains `GAMEVER_11` and `GAMEVER_10`, so a guard reads `#if
  DUKE3D_GAMEVER < GAMEVER_13D`, then `< GAMEVER_11`.
- 1.1 is done first, as a step back from 1.3D, all the way to demo sync. Then 1.0 is
  done as a step back from 1.1.
- The 1.3D test scripts and DOS capture tools are keyed by *edition* (`full`, `sw`).
  They gain the editions `sw11` and `sw10` instead of being copied.

Every difference found goes in the **Differences ledger** at the end of this file.

**Tech Stack:** C99, CMake ≥ 3.24 and CTest, SDL2, Python 3 (tests and tools). Research
uses Ghidra (the `~/Projects/ref/ghidra` project, run through `~/Projects/ref/tools/gh`),
`7zz`, and DOSBox-X with an emulated SB16.

**Spec:** `docs/superpowers/specs/2026-10-20-v10-v11-variant-design.md`

## Global Constraints

- Nothing from the 1.0 or 1.1 releases goes in the repo: no CONs, GRPs, demos, saves or
  executables. Tests read them from `DUKE3D_V10_SW_DATA_DIR` and
  `DUKE3D_V11_SW_DATA_DIR`.
- Numbers measured from the DOS executables may be committed: state values, addresses
  and checksums. Decompiled excerpts may be committed under `docs/v10-v11/notes/`. CON
  text may not.
- The 1.5, 1.4, 1.3D and 1.3D-sw builds keep their current behavior. The only exception
  is a real bug fix in shared code. That fix applies to all versions, gets a one-line
  comment next to it, and is called out in the commit message. Every existing test must
  pass in all four of those configurations at the end of every task that touches
  `source/`.
- The tree is not duplicated. Differences are `#if`/`#else` blocks in the existing files.
  A function too different to guard in place gets a separate version-only copy, as the
  1.3D `movetransports` (G13-A18) did.
- `1.0` and `1.1` are valid only with `DUKE3D_SHAREWARE=ON`.
- Engine changes are logged in `source/build/VENDORED.md`.
- Data-dependent tests are registered only when their data variable is set. This is the
  1.3D pattern. A data folder holding the wrong release fails with `wrong edition`.
- Work never runs inside `~/Downloads/DUKE3D10SW` or `~/Downloads/DUKE3D11SW`. Runs use
  scratch copies or symlinks, and the folder checksums are rechecked after DOSBox work.
- Commit messages follow `CLAUDE.md`: a subsystem prefix, one or two lines, and no
  metadata.
- Branch `v10-v11`, cut from `main`. The design commit is already on it.

## Review Focus

1. **A bad version setting**, `1.1` or `1.0` without `DUKE3D_SHAREWARE`, or `1.2`, must
   stop the configure step with a message naming the valid combinations. It must not
   build a registered 1.1. *Test: Task 7 step 1.*
2. **A data folder holding a different release** must fail with `wrong edition`. That
   covers 1.0 data under the 1.1 variable, 1.3D shareware under either one, or the
   reverse. It must not show up as a CON error or a desync. *Test: Task 8 step 1.*
3. **A demo from another version**, such as a 1.3D shareware demo or a 1.5 recording
   handed to the 1.1 build, must be refused with exit 2, not played as garbage. A 1.0
   demo in the 1.1 build is refused too, if Task 5 finds the headers can tell them
   apart. If they can't, the ledger records this as an accepted limitation, the way
   DOS behaved. *Test: Task 11 step 1.*
4. **A save from another version** (1.3D sw, 1.0 in the 1.1 build, a native 1.5 save)
   must be refused with a message. It must not crash or load corrupt state. *Test:
   Task 13 step 1.*
5. **Mixed multiplayer peers** must be refused at connect: 1.1 vs 1.0, 1.1 vs 1.3D sw,
   and 1.0 vs 1.5 sw. This holds even if their `BYTEVERSION`s collide. *Test: Task 14
   step 1.*
