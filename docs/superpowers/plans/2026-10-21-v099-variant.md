# Duke Nukem 3D 0.99 Beta Build Variant Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let `DUKE3D_VERSION` take `0.99` (shareware only). The build runs the beta's
unmodified CONs and plays all of E1 the way the DOS beta EXE does, checked by demos that
the DOS beta plays back. It also loads saves written by the DOS beta.

**Architecture:** This extends the 1.0/1.1 work one step further down:
- `gamever.h` gains `GAMEVER_099`. A guard reads `#if DUKE3D_GAMEVER < GAMEVER_10` and
  holds for 0.99 only. Every existing `< GAMEVER_11` / `< GAMEVER_13D` guard already
  covers 0.99, so it starts out as a 1.0 build.
- The test scripts and DOS tools are keyed by *edition*. They gain `sw099` instead of
  being copied.
- Unlike 1.0/1.1, the beta ships no demos. Playthrough demos are made by a route bot in
  our build, and the DOS beta's playback of each one is the reference (spec, "Demos").

Every difference found goes in the **Differences ledger** at the end of this file.

**Tech Stack:** C99, CMake ≥ 3.24 and CTest, SDL2, Python 3 (tests and tools). Research
uses Ghidra (`~/Projects/ref/ghidra`, run through `~/Projects/ref/tools/gh`) and DOSBox-X
with an emulated SB16.

**Spec:** `docs/superpowers/specs/2026-10-21-v099-variant-design.md`

## Global Constraints

- Nothing from the beta goes in the repo: no CONs, GRP, EXE, demos or saves. Tests read
  them from `DUKE3D_V099_SW_DATA_DIR` (`~/Downloads/d3d_beta`). Measured numbers (state
  values, addresses, checksums) may be committed. Decompiled excerpts may be committed
  under `docs/v099/notes/`. CON text may not.
- The 1.5, 1.4, 1.3D, 1.3D-sw, 1.1-sw and 1.0-sw builds keep their current behavior. The
  only exception is a real bug fix in shared code, which applies to all versions, gets a
  one-line comment, and is called out in the commit message. Every existing test must pass
  in all six existing configurations (`build-v15`, `build-v14`, `build-v13`, `build-v13sw`,
  `build-v11sw`, `build-v10sw`) at the end of every task that touches `source/`.
- No second copy of the tree: `#if`/`#else` blocks in the existing files. A function too
  different to guard in place gets a version-only copy, as before.
- `0.99` is valid only with `DUKE3D_SHAREWARE=ON`. It's a `VOLUMEONE` build.
- The beta's CONs are never edited, and no test uses edited CONs.
- A beta crash or hang is fixed, not copied *(user)*. The fix is guarded `< GAMEVER_10`,
  gets a ledger row marked `fix (departs from EXE)`, and a ruling in `docs/v099/rulings.md`.
- No multiplayer work and no network tests *(user)*.
- Engine changes are logged in `source/build/VENDORED.md`.
- Data tests are registered only when `DUKE3D_V099_SW_DATA_DIR` is set. Data that isn't
  the beta fails with `wrong edition`.
- Nothing runs inside `~/Downloads/d3d_beta` except writing the new `refdemos/` and
  `refsaves/` folders. Runs use scratch copies or symlinks. The Task 1 checksums are
  rechecked after each DOSBox session.
- Commit messages follow `CLAUDE.md`: a subsystem prefix, one or two lines, no metadata.
- Branch `v099`, cut from `main`. The design commit is already on `main`.

## Review Focus

1. **`0.99` without `DUKE3D_SHAREWARE`, or a typo such as `0.9`,** stops the configure step
   with a message naming the valid combinations. *Test: Task 6 step 1.*
2. **The 1.0 data folder given as the beta's**, or the beta given to a 1.0 build, fails with
   `wrong edition`, not a CON error or a desync. *Test: Task 6 step 1
   (`v099_edition_mismatch`).*
3. **A 1.0 demo or a 1.5 demo handed to the 0.99 build** is refused with exit 2. If Task 2
   finds that 0.99 and 1.0 headers can't be told apart, the ledger records that as an
   accepted limitation, the way DOS behaved. *Test: Task 10 step 1.*
4. **A 1.0 save loaded in the 0.99 build, or a 0.99 save loaded in the 1.0 build,** is
   refused with a message. It must not crash or load corrupt state. *Test: Task 14 step 1.*
5. **Playing on past the boss to the episode end** doesn't crash or hang, even though the
   DOS beta might. *Test: Task 13 step 1.*

### 1.0 build bugs found (fix for all affected versions in Task 9)

Found while comparing the beta with 1.0: places where our 1.0-sw build differs from `sw10.bin`.

- **Unaimed SHRINKER `zvel`.** 1.0 multiplies by **100** (`imul edi,edx,0x64`, sw10 `0x40f4d`; the beta too, `0x3cdbf`). Our shared `< GAMEVER_13D` shoot (`player.c`) uses ×97, which is right for 1.1 (sw11 `0x41941`, `lea`/`shl` ×97, G11-L31). 1.3D has its own copy. Affected: 1.0-sw (and 0.99). Fix: ×100 under `< GAMEVER_11`.

Checked and not bugs (no change):
- `ifsquished` with no `ud.clipping` test (sw10 `0x23470`; 1.1 `0x239f6` has it): 1.0 has no `clip` cheat, so `ud.clipping` stays 0 (G10-G05). 0.99 has the cheat: G099-055.
- `movefallers` with no OOZFILTER (sw10 `0x257fc`–`0x25811`, 1.1 `0x25e1c`–`0x25e31`; 1.3D-sw has it, `0x277ef`): no OOZFILTER in the 1.0, 1.1 or beta maps (G11-A96).
- `movestandables` with no `sect < 0` kill (sw10 `0x25aa0`, 1.1 `0x260d0`; 1.3D-sw has it, `0x27ad6`): only reachable with a sprite in no sector, where 1.0 would index `sector[-1]`. Keep the kill.
- `moveplayers` storing `bpos` for every player sprite after the shade (sw10 `0x25274`, 1.1 `0x25891`, beta `0x11e5c`): render interpolation, already ruled n/a (G11-A98).
- SPIT loogie positions `krand % (xdim-1)` / `% (ydim-1)` (sw10 `0x28189`, `0x281c4`; 1.1 `0x287cc`): display only and resolution-dependent in our port; same krand count (G11-A98).
