# macOS app bundle and native launcher

Date: 2026-10-23
Status: Approved by the user, 2026-10-23

Builder review: completed; no important unanswered planning questions.

## Intent and agreed scope

Provide a Finder-launchable macOS application with a small SwiftUI frontend
that selects a Duke installation and launches the existing C game or BUILD
editor as a separate process. The user approved using an external installation
in place and making bundled game data optional. Do not import or duplicate
external installations.

Keep the command-line executables and Windows/Linux builds working. This work
does not implement the separate runtime-release-selection design, a mod manager,
automatic installation discovery, an installer, or an App Store submission.
Never commit proprietary game data.

## Approaches

1. **SwiftUI launcher plus game/editor subprocesses. Selected by the user.**
   Native folder selection and preferences, with SDL retaining its own process
   and main thread. Requires bundling and managing two helper executables.
2. **An AppKit folder picker inside the game.** Smaller for a single prompt,
   but couples native application startup to the engine and does not provide
   one convenient entry point for both game and editor. Not selected.
3. **Run the game inside the SwiftUI process.** Requires coordinating Cocoa
   and SDL event loops and shutdown. Unnecessary for this launcher; not selected.

## Bundle and build

Add an opt-in `DUKE3D_MACOS_APP` CMake option, default OFF. With it enabled on
macOS, also build `Duke Nukem 3D.app`; retain `bin/duke3d` and `bin/build`.
Requesting the option on another platform fails with a clear configure error.
Enable Swift only for the macOS app option. Continue using CMake for all build
and packaging steps; do not require a separately maintained Xcode project.

Bundle layout:

- `Contents/MacOS/DukeLauncher`: SwiftUI application and main bundle executable.
- `Contents/MacOS/duke3d` and `Contents/MacOS/build`: existing C executables.
- `Contents/Resources/AppIcon.icns`: macOS icon derived from the classic Duke icon.
- `Contents/Resources/GameData/`: optional supplied data directory.
- `Contents/Info.plist`: stable bundle identifier, icon, app version and compiled
  Duke release/shareware metadata generated by CMake.

Proposed build defaults: macOS 12.0 minimum for app builds, targeting the
configured architecture. Universal binaries and notarization are later work.
App builds must be self-contained: use the existing fetched static SDL2 path
(`DUKE3D_FETCH_SDL=ON`) and reject an app configuration using an external dynamic
SDL instead of silently shipping a Homebrew dependency. Leave normal CLI builds'
SDL policy unchanged. Build the app icon reproducibly with macOS tooling;
check generated output visually at small and large sizes.

Add `DUKE3D_MACOS_GAME_DATA_DIR`, an optional directory supplied at configure
time. It is empty by default. If set, copy its contents to `GameData` while
packaging, excluding nothing implicitly. Use a fresh staged bundle so deleting
or changing the source directory cannot leave stale packaged files. Reject an
unreadable/non-directory path. No data is fetched automatically. Data is inserted
before any signing step; the running launcher never changes the app bundle.

## Data selection and validation

On first launch, use valid bundled data if present; otherwise show the folder
chooser. The chooser selects a directory, not individual GRP/CON files. It
accepts spaces, non-ASCII characters and paths on external volumes. Remember
one external selection using a Foundation bookmark in launcher preferences;
no multi-installation library in this version.

An explicit external selection takes precedence over bundled data. Provide
`Choose Folder…` and, when bundled data exists, `Use Bundled Data`. If a remembered
folder is missing, inaccessible or invalid, display the problem and let the
user choose again; do not silently launch a different installation. Canceling
the chooser preserves the previous selection. Refresh stale bookmarks when
they resolve; failure to resolve requests another selection.

The UI shows the active data source, its path, the compiled game release and
validation result, with `Play` and `Open BUILD` actions. Native folder selection
uses NSOpenPanel. Keep the UI small and use standard system controls. No graphics,
input or game-configuration page is needed; those settings remain in the game.

Validation must use the game's rules rather than an independent Swift copy of
the GRP fingerprint table. Add an early, noninteractive `-checkdata` game mode
that honors `-datadir`, runs before SDL initialization and returns diagnostics
on stdout/stderr. It checks that the base GRP can be read and has a structurally
valid directory with member ranges within the file. Check the known size/CRC
fingerprints against the compiled release. A known incompatible or recognized
unsupported release fails validation with the release names. Structurally valid
unknown/modified GRPs retain current compatibility policy: allow them, identify
them as unrecognized, and state the release this executable implements.

For Play, required standard scripts must be available as loose files or GRP
members; DUKE.RTS and demos are optional. Preserve case-insensitive filename
handling. BUILD checks the base GRP and required engine assets, without requiring
the game's CON scripts. The check mode accepts a narrowly scoped editor-check
flag so both actions share the same executable and validation implementation.
Return exit code 0 when usable, 1 for missing/unreadable/malformed data and 2 for
a known release mismatch. Diagnostics are human-readable; Swift uses exit status
and displays the text, with no parsing of prose or invented JSON protocol.

The launcher invokes this mode asynchronously for the selected action. Cache
only within the current validation operation; revalidate when launching so a
removed volume or changed installation is reported. Disable game/editor launch
when their validation fails. Disable BUILD for a compiled shareware build and
explain why. There is one compiled release per app; selecting a GRP does not
switch versions or choose another executable.

## Read paths and writable files

Introduce a shared, portable `-datadir DIRECTORY` startup option for the C game
and editor. Parse and consume it before either legacy argument parser and
before any GRP/resource load. Missing, repeated or unreadable-directory arguments
fail clearly. Resolve relative directories against the initial working directory.
Preserve all other argument ordering, including editor map and renderer arguments.

With this option, the selected directory is authoritative for the base GRP.
Keep the process working directory independent: read loose assets there first,
then loose assets in the selected data directory, then GRP members, preserving
existing GRP-only lookup restrictions. Absolute filenames stay absolute. Cover
direct read paths as well as `kopen4load`: group startup, scripts/CON includes,
ART reopening, palettes/tables, editor names and legacy setup.dat import, RTS,
and demo playback. Do not turn a read fallback into a write redirect. The
builder may choose the smallest shared resolver and API that cover these reads;
do not introduce a general mount system.

Without `-datadir`, retain existing CLI working-directory behavior. Remove the
old macOS executable-path heuristic that changes to the .app root; the launcher
owns the bundle data-location decision. CLI executables need no Foundation or
Swift dependency.

The launcher sets the child working directory as follows:

- External data: the selected installation directory, used in place. Existing
  demo, map, backup and relative custom-file behavior remains available there.
- Bundled data: `~/Library/Application Support/Duke Nukem 3D/Workspace/`, created
  on demand. Relative demo/map/backup writes go here, while bundled data supplies
  read fallbacks. This workspace also supplies loose overrides for bundled data.

Game configuration, saves and screenshots, and the editor's build.cfg retain
their existing Application Support locations. No ordinary launch, recording,
save, editor backup or map-save path may modify `Contents/Resources`. Fail
clearly if the workspace cannot be created. Do not copy or symlink bundled game
assets into the workspace. A read-only external installation can still Play;
report write failures rather than pretending maps/demos were saved there.

## Child process and launcher lifecycle

Use Foundation Process with an executable URL, argument array, explicit working
directory and inherited environment. Do not use a shell. Resolve executable and
resource locations relative to Bundle, so moving or renaming the app works.
The app is distributed outside App Sandbox in this version; no sandbox
entitlements or security-scoped subprocess access scheme are introduced.

Allow one running game/editor child per launcher. Disable launch buttons while
it runs, hide the launcher window after successful startup and restore/activate
it on termination. Reopening the app while a child runs activates that child
rather than starting another. Normal child exit returns to the launcher;
launch exceptions, nonzero exit or signal termination show an error with access
to the captured log. Treat startup failures currently exiting with status 0
as a validation problem where possible; do not promise that every legacy exit
code identifies success.

Write child stdout/stderr directly to a last-run log under
`~/Library/Logs/Duke Nukem 3D/`; use a separate temporary capture for validation.
Do not leave unread pipes that can block a child. The launcher remains responsive
while checks and children run. Closing the idle window quits the launcher.
Quitting while a child is active offers to cancel or terminate that child;
closing/hiding the launcher must not silently kill an editing session.

## Verification and delivery

1. Exercise startup argument consumption and data reads with disposable GRPs,
   loose files and directories, including spaces/non-ASCII names and missing,
   malformed and mismatched data. Ensure reads can use an external data directory
   while writes remain in the working directory. Verify no-option CLI behavior.
2. Exercise data-source precedence, bookmark failure/cancel paths and child
   argument/working-directory construction in Swift tests. Do not require
   proprietary data or a live GUI for these checks.
3. Build the optional app with and without fixture data, inspect Info.plist,
   icon and helper binaries, and ensure no non-system dynamic dependency points
   outside the bundle. Repackage after changing/removing fixture data to check
   that stale files are absent.
4. Launch the packaged app through Finder/LaunchServices from a different
   working directory; check folder selection, remembered and bundled sources,
   window/focus lifecycle, logs and failure messages. Visually inspect the UI.
5. With locally available matching game data, launch the game and editor and
   verify outputs leave a read-only bundle unchanged. Keep these data-dependent
   checks optional and report when they cannot run.
6. Run the existing native CTest suite and Windows cross-build after shared C
   changes. Keep default CI artifacts free of game data; document app build
   commands and optional data packaging in README.

## Builder choices and remaining scope

File decomposition, Swift testing harness, exact names of internal C helpers,
window spacing and control placement are builder decisions. The deployment
target, static SDL requirement, workspace behavior, validation CLI and child
lifecycle above are implementation defaults approved with this design.
