# 1.0 vs 1.1: CON interpreter differences

I compared `parse` in 1.0 (`0x34840`, jump table `0x34670`, opcodes 2–92) against 1.1 case
by case. I used the address-masked disassembly first, then the decompiles for the cases
whose instruction sequences differed. Apart from what is listed here, each case is the same
as 1.1 (`1.1-con-interpreter.md`). That includes every 1.1-vs-1.3D difference listed
there: `fall`, `debris`, `addphealth`, `spawn`, `spritepal`, `addkills`, `ifrespawn`,
`ifnotmoving`, `globalsound`, inventory item 5, and the new opcodes 65, 68, 69, 83 and 84.

1.0 globals:
- `insptr` `0x12e168`; `g_sp` `0xd1fa8`; `g_p` `0xd1fbe`; `g_i` `0xd1fbc`
- `ps[]` `0x112ab0`; `krand` `0x661e7`

## Differences

| Opcode | 1.1 | 1.0 | Evidence |
|---|---|---|---|
| `ifcanshoottarget` (45) | wide probe when `(BOSS1 \|\| BOSS2) && xrepeat > 60` | wide probe for BOSS1 or BOSS2 at any size (no `xrepeat` test) | `0x348cc`–`0x348f6` |
| `debugprint` (1.0: 90; 1.1: 93) | `insptr++` | `insptr++; sound(rand() % 254)`. This is the Watcom C `rand()` at `0x97f61` (LCG `0x41c64e6d`), not `krand`. `0x51c20` is the non-positional sound routine. | `0x3769f`–`0x376b8` |
| `ifawayfromwall` (90 in 1.1) | exists | does not exist: opcode 90 is `debugprint` | jump table `0x34670` |
| unknown opcode | dump, then `gameexit(tempbuf)` | `gameexit("Run Time Error.")` | `0x377d8` (string `0xc16b4`) |
| `resetplayer` (42), multiplayer branch | `pickrandomspot`, `updatesector`, `setsprite`, … `resetinventory`, `resetweapons`, `setpal`. The `got_access` save is a no-op. | Saves `got_access` (`ps+0x2c0`). Then calls `0x47c00`, `0x47b50` and `0x47730`. fmatch (by order) identifies these as `resetinventory`, `resetweapons` and `pickrandomspot`. Then it restores `got_access` when `[0x130edf] == 1`, so in that mode the keys survive the reset if either reset function clears them (not checked). Then `setsprite` (`0x60653`) **before** `updatesector` (`0x641c6`), then the sprite and hittype stores, and the sprite x/y/z copies last. There is no `cameradist`/`cameraclock` store. | call sites `0x35d5e`, `0x35d6a`, `0x35d76`, `0x35e5f`, `0x35f4e`; `fmap10.txt` |

Watcom's `rand` (`0x97f61`) obtains its state address from the getter at `0x97f5b`:
`0xd0a8c`, initially `1`. It updates that unsigned 32-bit state with
`state = state * 0x41c64e6d + 0x3039` and returns `(state >> 16) & 0x7fff`.
The first results are 16838, 5758, 10113 and 17515. No direct call to `srand`
(`0x97f85`) occurs in the flattened executable. The 18 direct calls to `rand` include
the opcode at `0x376a4`, weapon drawing and sound pitch. The 1.0 build therefore routes
all game-layer `rand()` calls through one Watcom stream, with its initial seed kept
for the process lifetime. The native multiplayer backend keeps its own host RNG;
its seeding and transport calls are outside this DOS game stream.

The same-as-1.1 checks outside `parse` are LIZTROOP pal handling and GREENSLIME
`extra = 10` (`spawn` `0x192f1`–`0x19342`), and the missing RPG smoke (`moveweapons`
`0x27890`; its only SMALLSMOKE spawn is `0x27f33`).
