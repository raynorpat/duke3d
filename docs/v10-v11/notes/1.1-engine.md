# 1.1 and 1.0 vs 1.3D: engine logic differences

Scope: the engine functions that affect game state. These are the spec step 3 list
(clipmove, getzrange, hitscan, inside, cansee, neartag, pushmove, updatesector, the sqrt
tables and slope functions), `krand`, the LZW pair and their readers and writers. Also
covered are the helpers those functions and the `move*` code call: lintersect, rintersect,
rotatepoint, nextsectorneighborz, dragpoint, getangle, the sprite-list functions,
clipinsidebox(line), keepaway, raytrace and lastwall. Rendering is out of scope, as it was
for 1.3D.

## Method

1. **Pair each function.** I paired every function across `sw13.bin`, `sw11.bin` and
   `sw10.bin` with `fmap11.txt`/`fmap10.txt` (fmatch, Task 2). The 1.3D sw names come from
   `docs/v13d/reference.md`. I named the remaining helpers from call targets: sw13
   clipmove calls `0x67f61`, `0x605d5`, `0x6997c` and `0x698d9`, and pushmove calls
   `0x604ea`. The sprite-list functions were placed by source order between anchors. 1.0
   has no fmatch partner for clipmove or pushmove; I found them from callers and source
   order (see the 1.0 section).
2. **Compare the instructions.** A script (capstone) disassembled each function in both
   images and normalized the operands:
   - jump targets inside the function become offsets
   - call targets become the matched sw13 function, or `F?` when unmatched
   - data addresses in `0x10000`–`0x2e0000` are masked (except multiples of `0x1000`)

   It then diffed the instruction sequences. **An empty diff means same code:** same
   instructions in the same order, with only the addresses of globals moved.
3. **Read every non-empty diff.** For logic functions I read them in the disassembly and
   in the Ghidra decompile (scratch output, out of tree), and
   compared each against the recreation sources in `~/Projects/ref/rev/` and this tree's
   `engine.c`.

Recreation revisions: between `19960305` and `19960419`, the only logic function whose
source differs is `inside`. cansee, hitscan, neartag, clipmove, keepaway, raytrace,
pushmove, getzrange, lintersect, rintersect, updatesector, rotatepoint, krand, the slope
functions, the sprite functions, clipinsidebox(line), initksqrt and ksqrt all have
identical bodies (`cfunc.py`, compared by md5).

Notes on the table:
- **"(tail)":** one side ends with `jmp` into another function's shared epilogue
  (`pop ebp; pop edi; pop esi; ret n`), the other has the epilogue inline. Examples:
  sw13 neartag `0x67e4c` → `0x659ea`; 1.0 lintersect `0x6263e`. This is a link
  difference only.
- **"(layout)":** 1.0 keeps `clipit` as four separate long arrays: x1 `0x132ddc`, y1
  `0x13a88c`, x2 `0x1325dc`, y2 `0x13a08c`, with `clipobjectval` at `0x139c8c`. 1.1/1.3D
  use one 16-byte struct array (`shl 4` at 1.1 `0x653f2`). Each element is the same
  value, so the logic is identical.
- **What carries over unchanged:** E-001/E-002 (2048-entry Newton `sqrtable`,
  `ksqrtasm`), E-003 (slopes), E-005 (no `updatesector` at the clipmove early return) and
  E-012 (1996 LZW) all hold for 1.1 and 1.0, because those functions' code is the same as
  1.3D sw's.

## 1.1 vs 1.3D

**inside** (E11-001) is the only logic difference. 1.1 has the recreation's
`LIBVER_BUILDREV < 19960320L` branch (the recreation clone's ENGINE.C:4582–4621; in rev/19960305/ENGINE.C `inside` is at
line 3088):

```c
char cnt; ...
if ((x1^x2) < 0) cnt ^= (x1*y2<x2*y1)^(y1<y2);
else if (x1 >= 0) cnt ^= 1;
...
return(cnt);
```

Evidence:
- 1.1 `0x5dafd`–`0x5db11`: `cmp edi,edx; setl dl; cmp ecx,esi; setl dh; xor dl,dh;
  xor bl,dl`, then `test edi,edi; jl; xor bl,1`. The result is the byte `bl` (`0x5db22`).
- 1.3D sw `0x60db5`–`0x60dc1`: `sub; sub; xor; xor`, then `not edi; xor ebx,edi`, and
  `setl` on the sign (`0x60dd1`).

This tree's E-004 form gives the same answer unless `x1*y2`, `x2*y1` or `y1-y2`
overflows 32 bits.

Non-logic corroboration of the date:
- 1.1 `allocache` (`0x718c9`) has no `newbytes = (newbytes+15)&~15`. The recreation
  guards that rounding `>= 19960319L` (CACHE1D.C:97). 1.3D sw `0x75f37` has
  `lea eax,[edx+0xf]; and al,0xf0`; 1.1 has `mov eax,edx` at `0x718d3`.
- Rendering functions differ too (for example 1.1 `0x687e8` vs sw13 `0x6ccd8`, after setview). They are out
  of scope.

## 1.0 vs 1.1

1.0's movement engine is older than every recreation revision. None of the differences
below has a recreation guard.

### cansee (E10-001)

1.0 `0x60c7a`:

```c
if ((x1 == x2) && (y1 == y2)) return(sect1 == sect2);
clipsectorlist[0] = sect1; danum = 1;
for (dacnt...) for (each wall wal of clipsectorlist[dacnt], wal2 = &wall[wal->point2])
{
    if ((wal->y-y1)*(wal2->x-x1) > (wal->x-x1)*(wal2->y-y1)) continue;     /* 0x60d0f-0x60d20 */
    if (!lintersect(x1,y1,z1,x2,y2,z2,wal->x,wal->y,wal2->x,wal2->y,&x,&y,&z)) continue; /* 0x60d5f */
    nexts = wal->nextsector;
    if ((nexts < 0) || (wal->cstat&32)) return(0);
    getzsofslope(dasectnum,x,y,&cz,&fz); if ((z <= cz) || (z >= fz)) return(0);
    getzsofslope(nexts,x,y,&cz,&fz);     if ((z <= cz) || (z >= fz)) return(0);
    add nexts to clipsectorlist if absent;
}
return(sect2 is in clipsectorlist);
```

1.1/1.3D compute `bot`, `t` and `u` inline and require `bot > 0` (`0x61f99`). Without
overflow, the two forms differ only when (x1,y1) lies exactly on a wall's line. 1.0 lets
that wall through in both crossing directions, with the hit at t = 0; 1.1 lets it through
only when crossing outward. Overflow can change other cases too, because the products are
formed differently.

### hitscan (E10-002)

1.0 `0x60e59` takes 13 arguments, with **no `cliptype`**:
- **Fixed masks.** It tests walls with `cstat&64` (`0x615e7`) and sprites with
  `cstat&256` (`0x616dd`, `test byte [cstat+1],1`). The wall-sprite one-sided test uses
  `cstat&64` (`0x619c0`), and floor sprites likewise (`0x61b4d`). That is `CLIPMASK1`
  for every call.
- **Partial reset.** At entry it sets only `*hitsect = -1` (`0x60e69`). `*hitwall` and
  `*hitsprite` keep the caller's values until something is hit; every hit writes all
  three. 1.1 sets all three (`0x62218`–`0x62230`).
- **Constant goal.** `*hitx = *hity = 0x1fffffff` (`0x60e86`, `0x60e9c`). This is the
  same value as `hitscangoalx`/`hitscangoaly`, which the game never changes.
- **The rest matches.** Ceiling and floor (flat and sloped), walls via rintersect,
  sprites of type 0, 16 and 32, the distance compares and the sector walk all follow the
  19960419 source line for line.

### clipmove (E10-003, E10-004)

1.0 splits clipmove into three functions:
- `0x62836`: the trace and sector search (callers: movesprite `0x23c30`,
  processinput `0x441e0`, `0x1fcd0` and `0x2db00`)
- `0x62bdb`: gathers the clip lines
- `0x63b11`: `addclipline`

Compared with the 1.3D source:
- **E10-003. `*sectnum < 0` is not rejected.** The outer function returns early only
  when `(xvect|yvect) == 0` (`0x62854`–`0x62858`). The gatherer sets `clipnum = 0`
  (`0x62bed`), then skips all work when `sectnum < 0` (`0x62bf4` `jl 0x63b06`). The trace
  then finds no clip line, so the move goes all the way to the goal. The sector search
  then runs:
  - first over a **stale** `clipsectorlist[0..clipsectnum)` (`clipsectnum` `0x22bb28`, `0x62ad8`), left by the previous engine
    call that filled it
  - then over every sector (`numsectors` `0x22bb4a`, loaded at `0x62af1`)
  - it returns 0

  1.3D returns 0 at once and leaves x, y and sectnum unchanged.
- **E10-004. Clip-line order.** The gatherer first walks the walls of every sector in
  `clipsectorlist`, adding sectors as it goes; the last wall clip line is at `0x630a8`.
  Only then does it walk the sprites of every listed sector, starting with the cliptype
  test at `0x6314f`. 1.3D handles walls then sprites per sector, inside one loop. The
  set of clip lines is the same, but the indices differ. `raytrace` walks
  `z = clipnum-1..0`, keeps a hit only when it is strictly nearer, and returns at once on
  its 256-step bailout, so equal-distance hits can choose a different `hitwall`. With it
  goes a different `clipobjectval` (the return value) and a different slide.
- **Same as 1.3D in every other detail:**
  - the floor/ceiling step tests
  - the `editstatus` gate (1.0 also runs the floor-step test when `clipyou` is already set
    by a one-sided or masked wall; it reads `sector[-1]` there, but cannot clear
    `clipyou`)
  - the wall clip boxes, sprite clip lines (0, 16, 32) and `rad`
  - the trace loop (`hitwalls[]` at `0x1339c4`, the `dmulscale6` reversal test, keepaway)
  - the final sector search

### cliptype as a 0/1 byte (E10-005)

1.0's getzrange (`0x661fb`), clipmove (`0x62bdb`) and pushmove (`0x63e01`) take a
**byte** `cliptype`:
- `0`: walls `cstat&1`, sprites `cstat&1`
- `1`: walls `cstat&64`, sprites `cstat&256`

These tests are at `0x62e38`, `0x6314f` and pushmove `0x63edc`–`0x63ef9`. They are
equal to `CLIPMASK0` and `CLIPMASK1`. Any other value clips against nothing, but no
1.0 call passes one that I saw. Otherwise:
- getzrange matches 19960419 line for line (walls first, then sprites, as in 1.3D).
- pushmove differs from 1.1 only in register allocation.

## Pins

- **1.1: `BUILD_ENGINEREV 19960220L`.** Its one logic difference (inside) fits the
  recreation guard `< 19960320L`. allocache fits `< 19960319L`. The release date is
  inside both ranges, and every guard this tree already has (`< 19960427L`,
  `< 19960820L`, `>= 19961112L`) resolves the way the 1.1 EXE behaves. So E11-001 is
  ported under `#if (BUILD_ENGINEREV < 19960320L)` and nothing else changes.
- **1.0: `BUILD_ENGINEREV 19960129L`.** E10-001 to E10-004 fit no recreation guard. They
  are guarded `#if (BUILD_ENGINEREV < 19960220L)`.
