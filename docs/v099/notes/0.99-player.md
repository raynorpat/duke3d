# 0.99 vs 1.0: player.c (and the weapon helpers)

Research snapshot: draft ledger statuses below describe the initial audit.
The current implementation status is in the [authoritative plan](../../superpowers/plans/2026-10-21-v099-variant.md#differences-ledger).

Scope: `source/player.c` as `docs/v10-v11/notes/1.0-player.md` maps it (setpal to
processinput), plus the weapon and inventory helpers that live in `actors.c`
(ceilingspace, addammo, addweapon, checkavailinven, checkavailweapon), and the full
`player_struct` field map. The baseline is this tree's 1.0 path (`DUKE3D_GAMEVER <
GAMEVER_11`), checked against `sw10.bin`. Every 0.99 difference below would sit under a
new `DUKE3D_GAMEVER < GAMEVER_10` guard inside the existing `< GAMEVER_11` / `<
GAMEVER_13D` blocks. Addresses are flat image addresses (base `0x10000`); "0.99" is
`beta099.bin`, "1.0" is `sw10.bin`.

## Method

1. **Pairing.** `fmap_beta099.txt` pairs all 22 player.c functions in order (setpal and
   checkweapons exact, the rest by order), and the actors.c helpers by address order.
2. **Field map first.** The 0.99 struct is `0x33f` bytes, so offsets shift. I aligned every
   fmatch pair (952) with masked operands, once with registers kept and once with them
   masked, and voted on `ps` offset pairs, both `[reg+off]` and `ps[k]+off` forms. Each
   field then got checked at its uses (`uses.py`, every access to every offset in both
   images). Every offset the beta code touches lands on a field start in the map below,
   except `0x271` (the high byte of `ang`) and `0x31f` (of `pycount`), which 1.0 also
   reads.
3. **Normalized diff.** Each pair was disassembled with capstone; calls mapped through
   fmap, data addresses masked, and every `ps` offset translated through the field map to
   its 1.0 offset (scratch `nd.py`), so the remaining hunks are real. I read every
   non-codegen hunk in the disassembly.
4. **Decompiles.** shoot, processinput, doincrements, getinput, aim, tracers, addweapon
   and checkavailweapon were also read side by side as Ghidra decompiles with the array
   bases symbolized (sprite, sector, wall, `ps` fields by name).

Scratch: `.superpowers/sdd/2026-10-21-v099-variant/scratch/t5-player/`.

Against 1.0 the beta drops `opyoff`, `truefz`, `truecz`, `wackedbyactor`, `scream_voice`,
`falling_counter` and `frag_ps` (20 bytes). It adds the per-player `pus`, `pub` and
`show_help` (5 bytes): `0x34e - 20 + 5 = 0x33f`. It also moves the byte block
`gm`…`palette` ahead of the shorts `rotscrnang`…`boot_amount`, the 1.3D order. The reference.md leads resolve as: `0x322` is `pus`,
`0x260` is `pals_time` used as an expiry clock, `0x2d8` is `timebeforeexit`.

### tracers (`0x3a990` / `0x3ea90`)

The beta has no `if ((klabs(x1-x2)+klabs(y1-y2)) < 3084) return;`. So a hitscan shot that
passes the `(krand()&7)==0 && lotag == 2` test always spawns its trail: 5 WATERBUBBLEs (3
krands each) or SMALLSMOKEs. **Sync** under water. Everything else matches the 1.0 form,
including the unset start sector.

### Slope operand verified during E1L3 replay

The current-position operand is the actual sector floor from getflorzofslope
(`j` in source), not the collision floor returned by getzrange (`fz`). Beta
`0x4030e` calls getflorzofslope and `0x4031b` preserves that result in ESI;
`0x40498` subtracts the probe floor from ESI before the two easing shifts.
A blocking floor sprite can make the two floors differ. The wrong operand
produced horizoff-455 versus DOS-16 near E1L3's duct, changing RPG height
before the first RNG divergence at tic6948. A synthetic slope/bridge fixture
checks collision floor32768 while requiring the measured horizon easing5.
