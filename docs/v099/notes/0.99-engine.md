# 0.99 vs 1.0: engine logic differences

Scope: the engine functions that affect game state, the same list as
`docs/v10-v11/notes/1.1-engine.md`: clipmove, getzrange, hitscan, inside, cansee, neartag,
pushmove, updatesector, the sqrt tables and slope functions, `krand`, the LZW pair and
their readers and writers, and the helpers those call. Rendering is out of scope.

The baseline is this tree's engine as the 1.0 build compiles it (`BUILD_ENGINEREV
19960129L`). That engine already matches the 1.0 EXE (`E10`/`E11` rows of the 1.0/1.1
ledger), so I compared the beta against `sw10.bin`, and read any difference against
`source/build/engine.c`.

Ledger rows: `E099-001` to `E099-014`.

## Method

1. **Pair each function.** `fmap_beta099.txt` (fmatch, Task 2) pairs every 1.0 address in
   the 1.1-engine.md table with a beta function, except `getceilzofslope` and
   `getflorzofslope`. Those two are the functions just before `getzsofslope` in both
   images, with the same sizes (`0xf9` bytes each).
2. **Compare the instructions.** A capstone script (scratch, out of tree) disassembled each
   pair and normalized the operands the way the 1.0 work did:
   - jumps inside the function become offsets
   - calls become the 1.0 function they map to through fmap, or `F?`
   - data addresses in `0x10000`–`0x2e0000` are masked (except multiples of `0x1000`)
   Address masking compares instruction shape. The mapped global layout and the
   executed input/output pairs below separately check the state interpretation.
3. **Check every remaining diff.** All but one function came out empty, or differed only
   in `F?` targets. I checked each `F?` by hand:
   - Tail jumps into a shared epilogue have the same instructions at both targets
     (for example `pop ebp; pop edi; pop esi; ret 0x24` at 1.0 `0x61f0a` and beta
     `0x5d241`).
   - `dfread`'s tail jump goes into `kdfread`'s identical tail (1.0 `0x70a31`, beta
     `0x4dd75`).
   - `dfwrite`'s six calls go to the C library `write` (1.0 `0x98445`, beta `0x70659`,
     both `0x1e6` bytes).
4. **hitscan** differs. I read it in the disassembly and the Ghidra decompile, and compared
   it line by line with `engine.c:hitscan`.
5. **Tables.** `TABLES.DAT` is in the GRP (8448 bytes). The beta's copy has the same MD5 as
   1.0's and 1.3D sw's (`97dbb2729be8ce9c967ec1e73864713f`). `PALETTE.DAT` and
   `LOOKUP.DAT` match too.

## hitscan (E099-001 to E099-004)

The beta's hitscan is 1.0's (E10-002) in its entry and in its wall and sprite parts.
It takes 13 arguments with no `cliptype` (`ret 0x24`), sets only `*hitsect = -1`
(`0x5c1d1`), and sets the goal to the constant `0x1fffffff` (`0x5c1ee`, `0x5c204`).
Walls use `cstat&64` and sprites `cstat&256`. The ceiling and floor parts differ in three
ways.

### No sign test on slopes (E099-001)

1.0 and this tree, for the ceiling and the floor:

```c
j = (vz<<8)-dmulscale15(dax,vy,-day,vx);
if (j != 0)
{
    i = ((sec->ceilingz-zs)<<8)+dmulscale15(dax,ys-wal->y,-day,xs-wal->x);
    if (((i^j) >= 0) && ((klabs(i)>>1) < klabs(j)))
```

The beta (ceiling `0x5c337`–`0x5c398`, floor `0x5c604`–`0x5c665`):

```c
    if (klabs(i>>1) < klabs(j))
```

1.0 has `mov eax,[j]; xor eax,ecx; test eax,eax; jl skip` (`0x6101e`–`0x61026`, floor
`0x61305`–`0x6130d`). The beta has no such test. So `divscale30(i,j)` can be negative,
and the beta takes the plane's intersection **behind** the start point (`i/j` in
`(-2, 0)`). That point then goes through the same nearer test and `inside` check as a
forward hit. For example, a shot aimed upward over a sloped floor can find the
floor plane behind the shooter. When that point is in the sector and nearer than the
other hits, the shot hits it. None of the recreation revisions (19960305 to 20000614)
lacks the test, so no guard exists for it.

### `klabs(i>>1)` (E099-002)

All four range tests halve before taking the absolute value:
- flat ceiling: `klabs((z1-zs)>>1) < -vz` (`0x5c40f`–`0x5c421`: `sar eax,1` then
  `neg`)
- flat floor: `klabs((z1-zs)>>1) < vz` (`0x5c6e4`)
- both slopes: `klabs(i>>1) < klabs(j)` (`0x5c382`, `0x5c64f`)

1.0 is `klabs(i)>>1` (`sar` after the `neg`, `0x6103a`, `0x610c9`, `0x61321`,
`0x613b0`). The two differ only when `i` is negative and odd: then
`klabs(i>>1) = (klabs(i)+1)>>1`, one more. The beta then rejects the one boundary case,
`klabs(i)>>1 == klabs(j)-1` (or `-vz-1`, `vz-1`), that 1.0 accepts. For flat
ceilings `i <= 0` always applies; for flat floors `i >= 0`, so only the ceiling test can
differ there.

### No-hit sentinel (E099-003)

The beta starts `x1` at `0x3fffffff`, not `0x7fffffff` (`0x5c23e`, `0x5c50d`), and has
no `x1 != 0x7fffffff` test (1.0 `0x6110b`, `0x613f8`). With no ceiling or floor hit it
runs the nearer test with `x1 = 0x3fffffff` and a stale `y1` (`ebp`, never set on that
path). It can pass (for example with `ys` negative), and then `inside(0x3fffffff, y1,
sect)` runs. That `inside` (E11-001 form) returns 0: every wall's `x - 0x3fffffff` is
negative for map coordinates, so no crossing toggles the count. So no hit is ever
recorded from the sentinel, and the result is the same as 1.0's.

### The rest (E099-004)

I checked the rest against `engine.c:hitscan` in the decompile:
- the wall test, `rintersect`, the `<` nearer test, the one-sided and `cstat&64` hit,
  `getzsofslope` and the sector list
- sprites of type 0, 16 and 32, with their `<=` nearer tests, the `cstat&128` and
  `picanm` z offsets, the `cstat&64` one-sided tests and the four-edge crossing count
- the `continue` on a zero-length slope wall, which skips `tempshortcnt++` in both
  (beta `0x5c2c5` → `0x5d22a`, 1.0 `0x60f63` → `0x61ef3`)

Everything else differs only in register and stack-slot allocation.

## Pin

**0.99: `BUILD_ENGINEREV 19960104L`** (the EXE date). E099-001 and E099-002 fit no
existing guard and no recreation guard, so they are guarded
`#if (BUILD_ENGINEREV < 19960129L)`. Every guard this tree already has (`< 19960220L`,
`< 19960320L`, `< 19960427L`, `< 19960820L`, `>= 19960220L`, `>= 19961112L`) resolves
at `19960104L` the same way as at `19960129L`, which is how the beta behaves: it has 1.0's
engine apart from hitscan.
